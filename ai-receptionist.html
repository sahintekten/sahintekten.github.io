An AI receptionist that knows when to stay quiet

SEDA answers clinic enquiries on WhatsApp, Instagram and Messenger, qualifies each person and books a free consultation. It has been piloted with a cosmetic surgery clinic in Istanbul since July 2026. This page explains how it works, the problems we hit in production and what the numbers say. It also includes a phone agent that I built and tested end to end, which isn't in production yet.

The problem

Clinics in Turkey's health tourism sector advertise heavily on Instagram and Facebook. Every ad brings a wave of messages, and staff can't always answer them quickly. Slow replies cost clinics enquiries they have already paid for.

An AI that simply answers everything isn't the solution either. It has to quote the right prices, book real appointments, and above all know when not to talk: when a staff member has taken over, when a message arrives on a channel it shouldn't handle, or when it isn't sure.

How a message is handled

  1. 1

    A person messages the clinic on WhatsApp, Instagram or Messenger. Meta delivers it to GoHighLevel, which the clinic uses as its CRM, inbox and calendar.

  2. 2

    GoHighLevel forwards it to our FastAPI backend through a single signed webhook, so every message enters the system the same way.

  3. 3

    The router merges quick bursts of messages into one turn and drops duplicates.

  4. 4

    Gates decide whether the agent may answer at all: has a staff member taken over, is this channel and page enabled for the bot? If anything is unclear, it stays silent.

  5. 5

    The router adds context, including which ad the person came from, using a map of about 80 campaign links.

  6. 6

    The conversation goes to the agent on Retell AI, which runs on a Claude model with the clinic's knowledge base in its prompt. Sessions are pinned to a prompt version so a conversation doesn't change behaviour midway.

  7. 7

    The agent calls tools: check availability, book or cancel an appointment, take a note, send sample photos, look up earlier records.

  8. 8

    The reply goes back through GoHighLevel. Bookings land in the clinic's calendar and sync to Google Calendar, and the clinic owner gets a notification for each type of event.

Deciding when to stay silent

The most important design decision was to enforce the agent's boundaries in code, not only in its prompt. A prompt can be misread; a gate can't. Before the agent sees a message, the router checks whether a staff member has taken over the conversation, and whether this channel and page are enabled for the bot. If any check fails or anything is unclear, the system stays silent. We call this failing closed.

A few operating rules back this up. A dry-run switch lets us test changes without sending anything. We never simulate conversations against the live clinic. And we treat "published" and "live" as different things: after every prompt release we check the version that is actually being served.

We test the gates by breaking them. A mutation check script removes each of the 10 safety gates in turn, and the test suite has to fail every time; it does, 10 out of 10. If the tests still pass without a gate, the tests aren't good enough. Separately, there are 267 automated tests.

Three problems we solved in production

Old conversations, old prices

Because sessions are pinned to a prompt version, conversations that started before a pricing update kept quoting the old prices and links. We built a session-retirement mechanism with two criteria and retired 2,051 sessions in one go. Each new session starts with a summary of the old one, so nobody had to repeat themselves.

A WhatsApp template that kept breaking

A time variable in a WhatsApp message template kept going out wrong. Our fixes didn't help, because Meta's template approval window meant the old version kept being sent. We removed the time variable from the template body altogether, and the next 32 of 32 messages went out correctly.

A map card with outdated details

When the agent shared the clinic's location, the map preview showed the doctor's old title and photo. We switched to coordinate-based links, added a filter that cleans links before a message is sent, and retired the affected sessions.

Three decisions that shaped the system

Our own backend instead of a no-code tool

We started on Make, but the scenarios were fragile and impossible to test properly. Moving to our own FastAPI backend, with one signed entry point, gave us tests, version control and full control over behaviour.

One system for CRM, inbox and calendar

We had built our own CRM panel, but retired it in favour of GoHighLevel. It gives clinics the WhatsApp Business line, the inbox and the calendar in one white-labelled place, which is what they actually use day to day.

Behaviour guaranteed by code

Staff takeover, channel and page rules live in the router as gates, so when the bot stays silent is a guarantee rather than a hope. The prompt handles how it speaks; the code handles whether it speaks.

The phone agent

Alongside messaging, I built SEDA's phone agent. It answers incoming calls in Turkish, gives clinic information, checks availability, books and cancels appointments, takes messages and passes urgent cases to the clinic. It has been validated end to end with real test calls, but it isn't in production yet: the clinic's main line hasn't been routed to it, and we prioritised messaging for the pilot.

How a call is handled

  1. 1

    A call comes in over a SIP phone line (Verimor in Turkey, Telnyx in Ireland) to an agent built with Retell's Conversation Flow.

  2. 2

    The agent works through a graph of nodes, so each stage of the call, from greeting to booking, cancelling or an urgent case, has explicit rules. Clinic information comes from a knowledge base, which deliberately contains no prices.

  3. 3

    Each tool call goes to a webhook in Make, which identifies the clinic from the agent's ID and runs the calendar or CRM action.

  4. 4

    The result goes back to the agent, which only confirms an action once the tool reports success.

  5. 5

    After the call, an analysis step records the outcome and notifies the clinic.

Safeguards

Cancelling an appointment requires looking up the booking first, and ownership is checked against the caller's number. Requests that arrive without a clinic ID are rejected; we added this after one such request broke routing during testing. The agent never tells a caller that something is booked or cancelled until the tool confirms it.

Three problems I solved

A migration that was only half done

Moving the data layer touched three places at once: the Make configuration, the database and the slot ID type in the flow. They fell out of sync, and a real test booking failed with a 409 conflict. I wrote a three-layer migration checklist and made slot IDs opaque strings everywhere.

Two formats for one phone number

Cancellations failed the ownership check because one system stored numbers starting with 0 and another with +90. Normalising both to the last ten digits fixed it, which a test call confirmed.

A conversation with no way out

One agent tried to book without checking availability first, and the flow got stuck. I added a recovery path for failed bookings and a loop guard, and it then passed 4 of 4 simulations.

How I tested it

Real test calls end to end: information, availability and booking on 4 July 2026, and cancellation on 6 July. On top of that, an 11-scenario notification matrix, a 9-scenario simulation set in Turkish, and a daily reconciliation check in Make. We don't have production call metrics yet because the agent hasn't taken real calls.

To show the system in English, I also set up a fictional Dublin clinic as a demo on an Irish phone line.

Retell AI (Conversation Flow), Make, Verimor and Telnyx SIP lines, GoHighLevel calendar, WhatsApp notifications.

My role

I'm the product owner and designed how the agent behaves: its rules and prompts, the knowledge base and pricing, the gates, and the test and release discipline. I set up the GoHighLevel, Meta and WhatsApp Business integrations, run the relationship with the clinic, and lead our production fixes.

I designed and built the phone agent myself: the conversation flows, the knowledge base, the Make scenarios, the phone line setup and the test plan.

I built the FastAPI backend, directing much of the work through Claude Code: I write detailed task briefs for it to implement, test and deploy, and I review what it ships against the served version.

What I'd do differently

We never measured how fast staff replied before the agent went live, so we can report the agent's reply time but not the improvement. Next time I'd capture a baseline first.

I'd also build alerts for silent failures from day one. When an upstream service stops responding, the bot goes quiet by design, which is safe, but someone needs to know about it straight away.

What's next

Onboarding a second clinic, moving the phone agent onto the same backend, measuring conversion and no-show rates properly, and adding alerts for silent failures.
